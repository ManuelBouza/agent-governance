## Problem being corrected

T063 v6 produced the first technically complete six-arm run, but the inherited T054/T063 decision taxonomy treated `CONTROL 3/3` as both a quality expectation and a prerequisite for a valid qualification decision.

That was a specification defect. A fully measured CONTROL quality failure is not an execution-validity failure. V6 demonstrated the missing state directly:

```text
ADAPTIVE: 3/3 PASS
CONTROL:  2/3 PASS
all six children: execution_validity=VALID
```

The successor must therefore separate:

1. execution validity;
2. absolute quality of each profile;
3. comparative quality between profiles;
4. efficiency conditional on accepted quality.

No v6 attempt is rerun or rescored. V1-v6 remain historical planning/provenance evidence only.

## Research basis

The repository testing strategy already requires repeated trials for probabilistic agent behavior and investigation of material run-to-run instability. It also distinguishes capability evals from deterministic regression gates and requires clean trial isolation.

Current OpenAI evaluation guidance likewise emphasizes that comparison claims depend on the complete harness and budget, and that repeated attempts should be interpreted together with success and resource consumption rather than as a single deterministic capability observation:

- https://openai.com/index/trustworthy-third-party-evaluations-foundations/

NIST guidance for binomial proportions shows that small-sample confidence intervals remain wide, especially near 0% or 100% observed success:

- https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm

Therefore v7 will **not** pretend that a handful of repeated trials establishes population-level statistical non-inferiority. A formal non-inferiority claim would require a justified margin and substantially larger sample design. V7 is instead a fixed, replicated qualification calibration over three frozen task classes.

## Selected experimental design

Design class:

```text
FIXED-N REPLICATED ABSOLUTE-QUALITY GATE
+ MATCHED COMPARATIVE OBSERVATION
+ QUALITY-CONDITIONAL EFFICIENCY
```

The run contains four complete replicate blocks. Each block contains the same three probe classes and both profiles, for:

```text
4 replicates × 3 probes × 2 arms = 24 scored child attempts
```

Four replicates are selected as project-specific pilot policy because they provide repeated evidence while permitting exact 2/2 arm-order counterbalancing within every probe. This is not represented as an industry-standard sample size and is not used for a p-value or population-level confidence claim.

## Counterbalanced schedule

The exact schedule is frozen prospectively:

```text
Block 1
  P1 ADAPTIVE -> CONTROL
  P2 CONTROL  -> ADAPTIVE
  P3 ADAPTIVE -> CONTROL

Block 2
  P1 CONTROL  -> ADAPTIVE
  P2 ADAPTIVE -> CONTROL
  P3 CONTROL  -> ADAPTIVE

Block 3
  same as Block 1

Block 4
  same as Block 2
```

For every probe, ADAPTIVE runs first exactly twice and CONTROL runs first exactly twice.

Every arm uses a fresh App Server and fresh exact read-only child. The same frozen oracle/task content is used across replicates. Shared inputs may be immutable, but mutable session state is not shared.

## First-attempt rule

Every scheduled arm contributes exactly one quality attempt.

A valid quality FAIL:

```text
is preserved
is model-quality evidence
does NOT invalidate execution
does NOT stop the remaining fixed schedule
does NOT authorize a replacement/rerun
```

The existing same-child empty-rollout reattachment barrier remains a transport persistence retry, not a second provider/model attempt.

Any measurement/profile/runtime/permission validity failure remains fail-closed and stops the run without compensating scored calls.

## Absolute quality gate

Quality is defined by the frozen deterministic/oracle semantics, not by agreement with CONTROL.

Per profile and probe:

```text
QUALITY_QUALIFIED     = 4/4 first-attempt PASS
QUALITY_NOT_QUALIFIED = 0-3/4 first-attempt PASS
```

Global profile quality:

```text
ADAPTIVE quality qualified = 12/12 PASS + no reroute/profile-integrity defect
CONTROL  quality qualified = 12/12 PASS + no reroute/profile-integrity defect
```

The 100% threshold is intentional project policy for these narrow deterministic/oracle-scored tasks. It is a qualification gate, not an estimate that the true success probability is 100%.

## Complete pair taxonomy

Each probe receives one of four quality outcomes:

```text
BOTH_QUALIFIED
ADAPTIVE_ONLY_QUALIFIED
CONTROL_ONLY_QUALIFIED
NEITHER_QUALIFIED
```

A complete technically valid run always has a defined profile-quality state. CONTROL failure can no longer turn a complete run into `EXECUTION_INVALID`.

## Global pilot decision

For a complete 24-arm valid run, `pilot_decision` is exactly one of:

### `QUALIFIED_PROFILE_AND_USAGE_EFFICIENCY`

Require all:

- ADAPTIVE 12/12 quality qualified;
- CONTROL 12/12 quality qualified;
- every requested/resolved ADAPTIVE profile remains the frozen lower model tier with no reroute;
- no safety/authority/oracle/rework disqualifier;
- exact ADAPTIVE tokens per successful result are at least **10% lower** than CONTROL.

The 10% materiality floor is project policy chosen prospectively to avoid calling a trivial token delta an efficiency result. It is not a statistical-significance threshold or external standard.

### `QUALIFIED_PROFILE_ROUTING_ONLY`

Require ADAPTIVE 12/12 and CONTROL 12/12 with intact lower-tier ADAPTIVE profile resolution, but the exact-token-per-success improvement is less than 10%.

This supports the configured lower-tier routing result at accepted quality but not a material provider-neutral token-usage savings claim.

### `ADAPTIVE_QUALITY_QUALIFIED_CONTROL_DEFICIENT`

Use when ADAPTIVE is 12/12 quality qualified but CONTROL is not 12/12 quality qualified.

This is a positive absolute-quality result for the adaptive mapping and a negative baseline-quality result for root-equivalent CONTROL. It does **not** support an accepted-baseline efficiency claim.

### `NOT_QUALIFIED`

Use whenever ADAPTIVE is not 12/12 quality qualified or has a profile-integrity/reroute disqualifier, regardless of CONTROL performance.

### `null`

Reserved only for an incomplete/blocked run caused by measurement, runtime, profile resolution, permission, harness validity or other non-quality execution failure.

## Efficiency metrics

V7 reports raw and quality-adjusted operational usage separately.

For each profile/probe and globally:

```text
total_tokens
total_duration
pass_count
tokens_per_success   = total_tokens / pass_count, when pass_count > 0
duration_per_success = total_duration / pass_count, when pass_count > 0
```

Failed quality attempts remain in the numerator because they consumed real resources. This makes the metric useful for operational cost-per-success interpretation without rewriting failures away.

The accepted-quality 10% token gate is evaluated only when **both** global profiles are quality qualified; then both have 12 successes and the comparison is symmetric.

Current provider rate-card information may be recorded descriptively, but dollar/credit pricing is operationally volatile and is not a normative v7 qualification constant. V7 must not claim exact billed cost from incomplete billing telemetry.

## Statistical interpretation boundary

V7 intentionally makes no claim of:

- formal statistical non-inferiority;
- population-level superiority;
- a universal Luna/Terra/Sol mapping beyond the three frozen task classes;
- global R007 policy adoption.

The four-replicate design is a calibration gate. If v7 qualifies, the next scientific step is broader task-distribution validation, not endless repetition of the same three examples.

Descriptive confidence intervals may be reported later, but they do not change the frozen v7 decision rule.

## Execution-validity semantics

For v7:

```text
run_execution_validity = VALID
```

when all 24 scheduled children are fully measured and execution-valid, regardless of their PASS/FAIL quality results.

A complete run has:

```text
run_model_comparison_eligible = true
pilot_eligible = true
pilot_decision != null
```

A quality FAIL is represented only at child/profile quality level (`WORKER_QUALITY`). It is not promoted into a run-level execution failure.
