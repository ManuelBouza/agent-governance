## Convergence finding

The v9 handoff labels the terminal condition `HOST_CAPABILITY_PREFLIGHT`. That is correct as the immediate run gate, but the deeper Orchestrator classification is an **Execution Adapter workspace-ACL confound**.

Both canary traces show that the sandboxed process could not read or enumerate the disposable workspace root itself, not merely `.agents/skills/mx-canary/SKILL.md`:

- `Get-Content` on the Skill body returned `Access ... is denied`;
- `Get-ChildItem` on the current workspace root returned `Access ... is denied`;
- recursive/file enumeration of the workspace returned access denied;
- the same behavior occurred under logical `read-only` and `workspace-write`.

The harness created every canary/acceptance root with Python `tempfile.TemporaryDirectory()` below `%TEMP%`. The run used Python `3.13.14`.

Python 3.13 changed Windows `os.mkdir(..., 0o700)` semantics to apply an ACL limiting the created directory to the current user and administrators; this also affects `tempfile.mkdtemp`, which is the primitive used by `TemporaryDirectory`. Codex's public Windows-sandbox issue `openai/codex#19791` independently records `WinError 5 / Access is denied` for Python/pytest/tempfile-style private `0o700` temp directories under the restricted-token sandbox.

Exact Codex 0.149.0 source further shows:

- its Windows sandbox smoke tests use a normal user-profile workspace directory rather than a Python private temporary root;
- workspace `.agents` protection is a deny-**write** protection, not a blanket deny-read rule;
- the restricted-token backend applies capability/ACL rules to the workspace allow set.

Therefore the v9 result does **not** establish that the supported `unelevated` backend cannot read local Skill bodies. It establishes that the evaluation harness supplied a workspace root whose private ACL prevented the sandbox token from traversing/reading the workspace.
