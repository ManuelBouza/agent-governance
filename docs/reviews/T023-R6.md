## Convergence finding

The reported terminal selection result (`B0` and `B1` do not qualify) is **not accepted as evidence that the candidate presentations themselves fail activation on the intended host surface**.

V7 required scored activation to be derived from successful host-observable candidate-body read/use after discovery. The submitted raw traces instead show repeated attempts to read the candidate `SKILL.md` bodies through PowerShell/`rg`/`cmd` that were rejected by host execution policy. The harness then recorded zero host-observed candidate-body activation while retaining model self-reported activation only as a diagnostic field. The same sessions also exposed unrelated app/plugin catalog material through Codex MCP resource discovery.

This creates a host execution-envelope defect: the acceptance cell was allowed to consume the corpus even though the mechanism required to demonstrate candidate-body activation was not first proven operational under the selected sandbox/rules/configuration surface. The oracle semantics themselves need not be reinterpreted; the defect is that the harness lacked a fail-closed preflight capable of stopping before acceptance scoring when the required host-read/use path was unavailable or contaminated by unrelated tool surfaces.

Therefore:

- v7 remains immutable and closed;
- its 171 valid repetitions and capacity events are diagnostic evidence only for successor method design;
- no v7 observation may be imported into a successor acceptance score;
- `activation_recall = 0.0` is not carried forward as a candidate semantic finding;
- no topology is selected or rejected for release based on v7;
- re-entry is `Specify`.

## Cost finding

The run also demonstrated an avoidable cost envelope. Each scheduled observation opened a fresh Codex session, and inspected traces show substantial unrelated app/plugin catalog context plus repeated policy-rejected command attempts before a structured answer. This multiplied input/reasoning/tool-loop cost across the 182 total live invocations.

A successor method must reduce both dimensions of cost before another acceptance epoch:

1. **per-session cost** — prove a minimal host surface before acceptance, exclude unrelated Apps/remote-plugin surfaces where compatible with the target Skill semantics, prevent known policy-rejection loops, record token/tool-call telemetry, and bound rollout cost;
2. **session count** — pre-register exact futility stopping whenever already-observed results make qualification mathematically impossible under the unchanged thresholds.

Relevant current vendor documentation confirms that Codex `--ignore-user-config` does not disable execution-policy `.rules`; `--ignore-rules` is a separate control. It also documents Apps and the remote plugin catalog as enabled by default, and exposes rollout-budget tracking. See:

- https://developers.openai.com/codex/cli/reference
- https://developers.openai.com/codex/config-reference
- https://developers.openai.com/api/docs/guides/latest-model

Sequential-evaluation research also supports prospectively defined stopping rules to avoid fixed-size benchmark cost when the decision is already resolved: Ofir Arviv et al., *Stop Guessing When to Stop Testing: Efficient Model Evaluation with Just Enough Data*, Findings of ACL 2026, https://aclanthology.org/2026.findings-acl.43/ .
